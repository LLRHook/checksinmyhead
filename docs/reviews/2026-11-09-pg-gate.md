# PostgreSQL gate timing — 2026-11-09

Scope: BUG-1793644504, the `checks / Gate postgres` row. Base `5e877e3`. This note
records why the row timed out, what changed and the measured effect. It is local and
hosted-CI timing evidence only: no integrated V&V pass, capacity budget (FEAT-1793644502)
or production qualification is claimed.

## What failed

`main` runs 42365246558 and 42359772172 fail because `backend/internal/tab` reaches
Go's default 10-minute per-package alarm inside
`TestPostgresLifecycleMeasuredBudgets/paid_attachment_assignment`. No assertion fails.
The same package passed on PR run 42364117584, so the row passed or failed with runner
speed. Package seconds from the two retained `go-postgres.jsonl` reports:

| Package | Passing run 42364117584 | Failing run 42365246558 |
|---|---|---|
| `cmd/bill-service` | 330.9 | 527.5 |
| `internal/tab` | 483.7 | 600.1 (alarm) |
| `migrations` | 85.7 | 124.7 |
| `internal/startup` | 43.2 | 64.0 |

Three things sat at a limit on the slower runner:

- `internal/tab`: `TestPostgresLifecycleMeasuredBudgets/large` took 306.6s, then 459.4s.
  Its 300 measured finalizations account for about a third of that. The rest was two
  unmeasured 9 MB `lifecycleSnapshot` reads per sample.
- `cmd/bill-service`: `TestPostgresCurrencyCreationQueryAndLatencyTargets` took 312.8s,
  then 506.5s. That time is the measured creation work itself (1,200 requests).
- `internal/startup`: the bill-service subtest took 60.05s against a 60s build bound,
  because its cold non-race `go build` competed with eight race compilations.

Every recorded latency target was met in both runs (large-tab fresh p95 385–606 ms
against 750 ms; maximum creation p95 443–1,261 ms against 2 s). The failure was the
harness wall clock, not an operation budget.

## What changed

1. **Cheaper per-sample state witness (test only).** `lifecycleDigest` returns, for the
   same nine tables as `lifecycleSnapshot`, a row count and an ordered hash of every
   complete row. The representative and large cohorts compare it on all 100 samples and
   still compare the canonical JSON snapshot on the first sample of each cohort.
   `TestPostgresLifecycleDigestTracksCanonicalSnapshot` proves the digest moves with the
   canonical snapshot for a known-column change in each table, NULL versus empty text,
   one microsecond, the last digit of an exact numeric, row insert and delete, and an
   additive column while NULL and once populated, and that restoring rows restores it.
   Measured on the 100-bill fixture: canonical snapshot 205–508 ms, digest 22–35 ms.
2. **Warm service build.** The row runs `go build ./cmd/bill-service ./cmd/web-service`
   before the tests. The startup test keeps its 60s build bound.
3. **Explicit limits.** `-timeout=20m` per package and a 30-minute job bound replace
   Go's implicit 10 minutes and the 20-minute job bound. The creation package cannot be
   made cheaper without removing measured samples, and it reached 527.5s.

Unchanged: production code, the eight packages, three cohorts of 100 samples at each
volume, access-shape limits, and every operation target (200 ms, 750 ms, 100 ms, 2 s).

## Measured effect (local)

Apple silicon, 10 cores, Go 1.27.3, pinned PostgreSQL 17.11 image on loopback with a
tmpfs data directory, owned random schemas. The machine is faster than a hosted runner,
so absolute seconds are not a CI prediction; the before/after ratio is the evidence.

| Measurement | Before | After |
|---|---|---|
| `TestPostgresLifecycleMeasuredBudgets/large`, package alone | 250.4s | not rerun alone |
| Same subtest inside the full eight-package row | not run | 173.7s |
| `internal/tab` package inside the full row | not run | 332.7s |
| `cmd/bill-service` package inside the full row | not run | 296.4s |
| `TestPostgresServiceBinaryModes` | not run | 3.2s |
| Full row wall clock | not run | 5m36s |

The full row finished with 1,554 passing terminals, no failures and no skips, and the
gate helper accepted the report (`validate-reports --row postgres`). Large-tab fresh
p95 was 373–399 ms against 750 ms. Two digest controls fail as intended: omitting
`tab_settlements` and hashing only row ids.

The before figure was taken with the package running alone and the after figure under
full-row contention, so the saving in `large` is at least the 77s shown.

## Hosted confirmation

Pull request run 42697731004 (first run of this change) passed all six rows; the
PostgreSQL row reported 1,554 passing terminals. Its runner was slower than both
earlier runs, which makes it the useful case:

| Package | Seconds | Share of the old 600s | Share of the new 1,200s |
|---|---|---|---|
| `internal/tab` | 595.4 | 99% | 50% |
| `cmd/bill-service` | 560.0 | 93% | 47% |
| `internal/startup` | 6.4 | — | — |

`large` took 302.9s while its measured fresh p95 was 689–698 ms, nearly double the
385–420 ms of the earlier passing run; the unmeasured remainder fell from about
200s to about 100s. Without the digest the package would have passed the old alarm, and
without the explicit timeout the row would have depended on a five-second margin.
No latency miss was logged, but large-tab fresh p95 at 698 ms against 750 ms leaves
little margin on a slow runner; reducing that read is FEAT-1793644502.
